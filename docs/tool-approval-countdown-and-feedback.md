# 工具审批交互：动态倒计时、临时反馈与请求竞态

本文说明工具审批和补充提问在网页上的生命周期。它是对已有 Tool Registry、InteractionService 的交互补充，不改变工具权限和一次性审批规则。

## 1. 为什么之前的操作提示一直留在对话下面

前端 `AgentToolsPanel.vue` 将“已批准”“已拒绝”“答复已提交”保存到 `feedback`，但之前只有切换会话才会清空，没有自动消失的生命周期。

本次复现时，审批提交后服务端返回的待处理列表已经是空数组，审批卡片也已移除；6 秒后仍存在的是本地操作反馈，而不是服务端再次发来了审批。

因此要区分三类内容：

| 内容 | 页面生命周期 | 服务端数据 |
| --- | --- | --- |
| 待处理审批、待补充问题 | 只在等待用户响应期间显示 | 保留交互记录及状态 |
| “已批准／已拒绝／答复已提交” | 最多显示 4 秒；切换会话、生成状态变化或组件卸载可提前清理 | 不是新的聊天消息 |
| 任务计划、任务产物 | 可以继续查看，不随操作反馈一起消失 | 持久化业务数据 |

**不再显示审批卡片，不等于删除审批记录。** 服务端的审计和一次性票据仍按原有逻辑保存、消费和校验。

## 2. 倒计时从哪里来

服务端 `InteractionService.newInteraction` 生成 `expiresAt`：

```text
expiresAt = min(当前时间 + TOOL_HUMAN_TIMEOUT, 当前业务 Context 的截止时间)
```

`TOOL_HUMAN_TIMEOUT` 默认是 90 秒，但如果本轮生成只剩 30 秒，交互也不能再等待完整的 90 秒。前端读取这个实际截止时间，不自行创建另一个 90 秒期限。

前端每秒计算：

```ts
remainingSeconds = Math.max(0, Math.ceil((Date.parse(expiresAt) - Date.now()) / 1000))
```

展示规则：

- 90 秒：`剩余 1 分 30 秒`。
- 60 秒：`剩余 1 分 00 秒`。
- 59 秒：`剩余 59 秒`。
- 到期：移除可操作卡片，短暂显示等待到期的提示。

计算与格式化放在 `frontend/src/lib/tool-interaction.ts`，组件只负责驱动时钟和渲染。

### 为什么不能每秒直接减一

浏览器后台标签页、设备休眠和主线程繁忙都可能使定时器延迟。若每次回调只减一，现实中过了 30 秒，页面可能只减少了几秒。

现在定时器只是触发重新计算，真实剩余时间始终由 `expiresAt - Date.now()` 决定。窗口重新获得焦点或页面可见性变化时，也会立即重算，不等待下一次定时器回调。

倒计时使用等宽数字减少跳动，并设置 `role="timer"`、`aria-live="off"`，避免读屏软件每秒重复打断用户。没有新增闪烁或装饰动画。

## 3. 到期后前端和后端分别负责什么

前端到期后会移除操作入口、清理该问题的答复草稿，并刷新最新工具状态；即使用户在定时器回调前恰好点击，也会在提交前重新检查截止时间。

但前端时钟**不是权限边界**：

- 用户设备时钟可能有偏差，显示时间只能作为辅助。
- 服务端 Repository 只接受 `pending` 且 `expires_at > 服务端当前时间` 的响应。
- 待处理查询也只返回尚未到期的 `pending` 交互。
- Shell 真正执行前，Registry 仍要消费匹配任务、工具版本和完整参数的一次性审批票据。

不要因为前端隐藏了按钮，就认为审批已经在数据库中取消；也不要因为点击时按钮可见，就认为服务端一定会接受。最终结果由服务端确认。

### 点击后才到期怎么办

如果审批 POST 已发出、结果尚未返回，倒计时归零时不会直接宣称“审批超时”。页面继续禁用按钮，显示“正在确认处理结果…”。

原因是服务端可能已在有效期内接受请求，只是响应还在网络中。此时应该等服务端结果，再显示成功或失败，不能用客户端计时覆盖事实。

## 4. 操作反馈如何自动消失

`showFeedback()` 设置文字，并启动一个 4 秒的清理定时器。新反馈出现前先取消旧定时器，避免前一个提示的定时器误删后一个提示。

成功流程是：

```text
用户点击批准／拒绝
  → POST 提交，按钮禁用，等待服务端
  → 提交成功，立即移除该交互卡片
  → 显示最多 4 秒的确认反馈
  → 清空反馈；没有其他内容时整个工具面板消失
```

相同规则也用于“补充问题的答复已提交”。切换会话、生成状态变化和组件卸载时，都清理已有反馈及定时器。

错误则不自动按 4 秒消失：提交失败必须保留错误说明和仍然有效的重试入口，否则用户可能误以为操作已成功。后台状态轮询的错误单独放在 `loadError`，避免一次成功的轮询把提交失败的错误悄悄清除。

## 5. 为什么还需要处理旧请求

自动消失只解决可见症状。异步查询与操作请求还可能交错返回。

### 5.1 旧 GET 让审批重新出现

例如先发出待处理列表 GET，然后用户批准，POST 成功；最后，先前的 GET 才带着旧审批返回。

组件使用当前会话作用域内的 `dismissedIDs` 集合记录已成功提交或本地到期的交互 ID。合并查询结果前过滤这些 ID，避免刚消失的卡片又被旧响应带回来。它不是权限白名单，也不替代数据库状态。

### 5.2 切换 A → B → A 的旧 POST

只比较会话 ID 不够：用户从 A 切到 B，再回到 A，最初 A 的 POST 才完成，此时会话 ID 又相等了，但它已经不是原来的页面生命周期。

组件为每轮会话加载维护 `scopeVersion`。提交和产物预览开始时保存版本，完成后版本不匹配就不再更新页面。旧状态查询则通过 `AbortController` 取消。

这些保护只阻止过时结果污染页面，不会取消用户已成功提交给服务端的审批。

### 5.3 卸载后的定时器

计时器与事件监听都在对应 Vue `watch` 的清理回调中释放：

- 无待处理交互时，清理每秒时钟和窗口／页面监听。
- 会话切换或组件卸载时，取消旧 GET、清理轮询和反馈定时器。
- 正在执行的旧异步回调通过作用域版本校验忽略。

## 6. 代码阅读顺序

1. `frontend/src/lib/tool-interaction.ts`：剩余秒数、显示格式、反馈持续时长。
2. `frontend/src/components/AgentToolsPanel.vue`：时钟驱动、到期处理、反馈清理、提交与竞态保护。
3. `backend/internal/service/interaction.go`：交互有效期、响应校验、等待与取消。
4. `backend/internal/repository/agent_tool.go`：仅查询有效待处理交互，原子响应与一次性审批消费。
5. `design-system/agent-workspace/COMPONENTS.md`：后续界面保持一致的交互规范。

## 7. 验证方式与边界

仓库中的时间计算单元测试位于 `frontend/src/lib/tool-interaction.test.ts`，覆盖分钟／秒边界、后台时间跳跃、到期归零和无效时间。运行：

```bash
cd frontend
npm test
npm run build
```

本次另外使用真实浏览器、模拟接口和可控时钟验证了以下场景；这些浏览器检查不包含在上述 `npm test` 命令中：

- 倒计时会变化，批准和拒绝反馈会自动消失。
- 后台恢复时立即校时，到期不再提供操作入口。
- 提交失败保留重试，成功轮询不掩盖错误。
- 旧 GET 不复活审批，A → B → A 不显示旧 POST 的反馈。
- 提交中跨过截止时间仍等待服务端确认。
- 补充答复反馈自动清理，卸载后停止轮询。
- 375px、760px、1024px、1440px 无横向溢出，移动点击区域至少 44px，并检查减少动态效果设置。

这一版没有增加前后端时钟偏差校准，也没有新增审批历史查看页面。后续若要提供审批审计，应独立展示历史记录，不要把已处理的可操作卡片长期堆在对话末尾。
